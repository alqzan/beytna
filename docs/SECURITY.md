# الأمان — نموذج المصادقة والعضوية والبيانات (P0)

هذا المستند يشرح النموذج المُنفَّذ في هذا الفرع لإغلاق الوصول العام على بيانات
العائلة وبناء عضوية صحيحة. راجع أيضاً `docs/MIGRATION.md` لخطة النشر خطوة
بخطوة، و`firestore.rules` للقواعد الفعلية، و`tests/rules/security.test.mjs`
للاختبارات التي تثبت هذا النموذج ضد Firebase Emulator.

## المشكلة الأصلية

- التطبيق كان يقرأ/يكتب `families/beytna` — معرّف ثابت معروف مسبقاً.
- لا Firebase Auth إطلاقاً — أي طرف (بلا تسجيل دخول) يقدر يقرأ (وعلى الأغلب
  يكتب) هذا المستند لو كانت قواعد Firestore بوضع الاختبار (test mode) أو
  مفتوحة، وهذا ما أثبتته المراجعة.
- مفتاح `apiKey` في `firebaseConfig` **ليس سراً** — هذا تصميم Firebase
  المقصود (المفتاح يُعرِّف المشروع فقط، لا يمنح صلاحيات). الحماية الحقيقية
  الوحيدة هي **Firebase Auth + قواعد Firestore**، وهذا ما كان مفقوداً.

## النموذج الجديد

### ١. المصادقة: Firebase Anonymous Auth

- كل جهاز يسجّل دخول مجهول (`signInAnonymously`) تلقائياً عند أول فتح —
  بلا بريد إلكتروني ولا كلمة مرور، مناسب لتطبيق زوجين بسيط.
- `request.auth != null` شرط أساسي لأي قراءة/كتابة في القواعد.
- **حدود معروفة**: هوية Anonymous Auth مرتبطة بتخزين المتصفح (IndexedDB).
  مسح بيانات المتصفح = فقدان الهوية = يحتاج الجهاز دعوة جديدة للانضمام مرة
  أخرى. هذا مقايضة مقصودة لتفادي تعقيد بريد/كلمة مرور غير الضروري الآن.

### ٢. العائلة: معرّف عشوائي قوي، لا اسم ثابت

- `familyId = randomHex(16)` (١٢٨ بت من `crypto.getRandomValues`، ٣٢ حرف
  hex) — غير قابل للتخمين عملياً، ومختلف في كل مرة.
- القواعد تفرض `isStrongFamilyId()` (نمط `^[A-Za-z0-9_-]{20,64}$`) عند
  إنشاء عائلة جديدة، فلا يمكن حتى للعميل نفسه إنشاء عائلة بمعرّف قصير أو
  ثابت مثل `beytna`.
- `families/beytna` مقفول صراحة وبشكل دائم (`allow read, write: if false`
  على `families/beytna/{document=**}`) — دفاع إضافي فوق كون النموذج
  الجديد أصلاً لا يمنح عضوية تحت معرّف غير عشوائي.

### ٣. العضوية: صريحة، لا يمنحها العميل لنفسه

- `families/{familyId}/members/{uid}` — وثيقة عضوية لكل جهاز/مستخدم.
- إنشاء العائلة: الجهاز الأول يكتب `families/{familyId}` بنفسه كـ
  `ownerUid`، ثم يكتب `members/{uid}` لنفسه — القاعدة تتحقق أن
  `ownerUid == request.auth.uid` على مستند العائلة الموجود فعلاً.
- **لا يوجد مسار يسمح لعميل يعرف `familyId` فقط أن يمنح نفسه عضوية.** أي
  محاولة إنشاء `members/{uid}` بدون كونك `ownerUid` أو بدون دعوة صالحة
  تُرفض من القواعد (مُختبر صراحة).
- إبطال جهاز = حذف وثيقة عضويته (`allow delete: if isMember(familyId)`)
  — أي عضو حالي يقدر يبطل أي جهاز بما فيه جهازه (تسمح للزوجين المتساويين
  بإدارة الوصول بدون هرمية "مالك/عضو" معقّدة).
- **قيد معروف**: الجهاز المُبطَل لا يعرف فوراً أنه أُبطل ما لم تفشل قراءة
  نشطة لديه (rules تمنع فعلياً فوراً) أو يعيد فتح التطبيق — لا يوجد إشعار
  حي حالياً يوجّهه تلقائياً لشاشة الانضمام. موثّق كخطوة تحسين لاحقة.

### ٤. الدعوات: رمز عشوائي، لا يُخزَّن نصاً صريحاً، استخدام لمرة واحدة

- إنشاء العائلة أو "بيتك وأجهزتك" يولّد `token = randomHex(16)` (١٢٨ بت)
  ثم يحسب `tokenHash = SHA-256(token)` (عبر Web Crypto، محلياً في المتصفح).
- **الرمز نفسه لا يُكتب في Firestore أبداً** — معرّف المستند هو
  `tokenHash`، ومحتوى المستند لا يحوي الرمز الأصلي. هذا يحقق "hash لا
  plaintext" المطلوب.
- الرمز المشترك للنسخ/اللصق هو `familyId + '.' + token` — سلسلة واحدة
  يُلصقها المستخدم على الجهاز الثاني، بدل حقلين منفصلين.
- **استرداد الدعوة يُثبت الاستحقاق فعلياً عبر القواعد** (بديل Cloud
  Function مقصود لتفادي الحاجة لخطة Blaze/نشر Functions الآن): الجهاز
  المنضم يكتب `members/{uid}` **ويحدّث** `invites/{tokenHash}` بنفس
  الوقت عبر `writeBatch` ذرّي. القاعدة تسمح بإنشاء العضوية فقط إذا كانت
  الدعوة المُشار إليها (`joinedViaInvite`) موجودة، `used == false`، وغير
  منتهية — وتسمح بتحديث الدعوة لـ `used: true` فقط إذا كانت غير مستخدمة
  بعد. Firestore يرفض الدفعة (batch) بالكامل لو فشل أي شرط، فلا يمكن
  استخدام نفس الدعوة مرتين (مُختبر صراحة، بما فيه محاولة من جهاز ثالث).
- **لا `list` على الدعوات لغير الأعضاء** — لازم معرفة `tokenHash` (أي
  الرمز الأصلي) بالضبط لقراءة دعوة واحدة؛ لا سرد يكشف الدعوات الموجودة.
- انتهاء الصلاحية: ٧٢ ساعة افتراضياً، وحد أقصى ٧ أيام تفرضه القواعد.
- تدوير/إبطال دعوة: أي عضو يقدر يعلّم دعوة غير مستخدمة كـ `used: true`
  يدوياً (زر "إلغاء" في واجهة "بيتك وأجهزتك").

### ٥. القواعد: عضوية + عزل + تحقق شكل (schema)

راجع `firestore.rules` مباشرة. أهم النقاط:

- كل قراءة/كتابة تحت `families/{familyId}/**` تتطلب `isMember(familyId)`
  (ما عدا مسار إنشاء العائلة/العضوية الأولى، ومسار قراءة/استرداد دعوة
  بمعرفة الرمز الدقيق).
- `isMember()` = `exists(members/{request.auth.uid})` — عضو عائلة A لا
  يملك وثيقة في `members` تحت عائلة B، فلا يستطيع الوصول (مُختبر صراحة).
- `allow list: if false` على `families` نفسها بالكامل — منع تعداد
  العائلات مطلقاً.
- تحقق شكل (schema): أسماء حقول محصورة (`keys().hasOnly(...)`)، أنواع
  (`is string`/`is int`/`is timestamp`...)، وحدود حجم (طول نص، حجم
  مصفوفة/خريطة). **قيد معروف**: قواعد Firestore لا تدعم التكرار (loop)
  على عناصر مصفوفة/خريطة متغيّرة الحجم، فالتحقق العميق لكل عنصر داخل
  `sections.*` يبقى مسؤولية العميل + حد Firestore الطبيعي (١ ميغابايت لكل
  مستند)؛ القواعد تتحقق من الحد الأقصى لعدد العناصر/المفاتيح فقط. موثّق
  لتفادي الادعاء بتحقق أعمق مما هو موجود فعلاً.
- المقاضي (`shopping`) لها تحقق شكل أدق لأنها الآن subcollection مستقلة
  (سجل لكل غرض)، فيمكن التحقق من كل حقل فعلياً (انظر §٦).

### ٦. المقاضي: سجلات مستقلة بدل استبدال مصفوفة كاملة (P1)

المشكلة الأصلية: كل تعديل (إضافة/حذف/تعليم) كان يكتب **القائمة كاملة**
عبر `updateDoc(doc, {shopping: [...]})`. لو عدّل الجهازان في نفس اللحظة،
آخر كتابة تمحو تعديل الطرف الآخر بالكامل.

الحل: `families/{familyId}/shopping/{itemId}` — وثيقة مستقلة لكل غرض،
تحوي `name, category, completed, qty, note, createdAt, updatedAt,
updatedBy, deletedAt`. الحذف حذف ناعم (`deletedAt` بدل حذف صلب — القواعد
تمنع `delete` فعلياً) حتى يبقى "تراجع" ممكناً بدون فقدان `createdAt`
الأصلي.

`useShoppingCollection` في `index.html` يحافظ على نفس واجهة البرمجة
القديمة (`{items, update, remove, replaceAll}`) حتى لا تتغيّر مكوّنات
الواجهة، لكن الطبقة الأدنى تحوّل `replaceAll(nextArray)` إلى **فرق**
(diff) بين الحالة الحالية والمطلوبة عبر `diffShoppingUpdates()` في
`lib/core.mjs` (دالة صِرفة مُختبرة بوحدات منفصلة)، وتُنتج كتابات لكل
وثيقة متأثرة فقط ضمن `writeBatch` واحد — لا كتابة فوق القائمة كاملة أبداً.
مُختبر end-to-end عبر Playwright + Firebase Emulator: تعديلان متزامنان من
جهازين لعنصرين مختلفين لا يمحو أحدهما الآخر (انظر `tests/smoke/run.mjs`).

**قيد معروف / نطاق هذه الدورة**: التحويل لسجلات مستقلة تم لقسم "المقاضي"
الافتراضي فقط (الأكثر تعرّضاً للتعارض، كما طلب البريف صراحة). الأقسام
الأخرى (الملاحظات، السفر، الشنطة، الأقسام المخصّصة) ما زالت ضمن
`sections.{id}` كمصفوفة واحدة (استبدال كامل عند كل تعديل) — أقل عرضة
للتعارض عملياً لكنها ليست محصّنة بنفس القدر. موثّق كخطوة P1 تالية.

### ٧. حالة مزامنة صادقة

`SyncPill` في الواجهة تعتمد على `snapshot.metadata.hasPendingWrites` و
`snapshot.metadata.fromCache` الفعليين من Firestore (`includeMetadataChanges: true`)
بالإضافة لحالة `navigator.onLine` — لا تعني الأيقونة مجرد "بدأ SDK".
الحالات: تحميل / بلا اتصال / جاري الحفظ (pending) / محفوظ محلياً (cache)
/ متزامن / فشل الحفظ (مع زر إعادة محاولة).

نستخدم `persistentLocalCache` (تخزين Firestore المحلي الدائم) كـ
"outbox" فعلي بدل اختراع طابور كتابة يدوي — الكتابات أوفلاين تُحفظ محلياً
وتُرسل تلقائياً عند عودة الاتصال حتى بعد إغلاق الصفحة. طبقة `writeError`
الإضافية في `useShoppingCollection` تغطي تحديداً ما لا يغطيه طابور
Firestore التلقائي: فشلاً **دائماً** (صلاحيات مرفوضة مثلاً) لا يُعاد
محاولته تلقائياً — تُعرض رسالة صريحة + زر "إعادة المحاولة" بدل ادّعاء
النجاح.

### ٨. النسخ الاحتياطي والاستيراد (P1)

`lib/core.mjs`: `buildBackup`/`parseBackup`/`planImport` — دوال صِرفة
مُختبرة بوحدات (`tests/unit/core.test.mjs`). الملف يحوي `schemaVersion`،
`exportedAt`، و`checksum` (SHA-256 لمحتوى `data` فقط). **لا يحوي أي شيء
متعلق بـ Auth أو العضوية أو الدعوات** — فقط محتوى العائلة (أقسام +
مقاضي). الاستيراد يرفض صراحة (لا بصمت) checksum غير مطابق أو
`schemaVersion` غير معروف، ويعرض معاينة (عدد العناصر لكل قسم) قبل
التأكيد، مع خيار دمج (إضافة فوق الحالي بمعرّفات جديدة) أو استبدال كامل
(بتحذير صريح).

## ما لم يُنفَّذ عمداً في هذه الدورة (ولماذا)

- **لا حسابات بريد/كلمة مرور** — غير مطلوبة لنموذج "زوجين + جهازين"
  البسيط، وتضيف تعقيداً (تحقق بريد، استرجاع كلمة مرور) بلا فائدة أمنية
  إضافية هنا.
- **لا Cloud Functions** — استرداد الدعوة يمرّ عبر تصميم قواعد يثبت
  الاستحقاق فعلياً (transaction + get() عبر القواعد)، وهو البديل الصريح
  المسموح به في البريف، ويتفادى الحاجة لخطة Blaze ونشر Functions التي لا
  نملك صلاحية Firebase Console لتنفيذها الآن.
- **لا اكتشاف إبطال حي** للجهاز المُبطَل (راجع §٣) — الأمان الفعلي فوري
  (القواعد ترفض القراءة/الكتابة مباشرة)، لكن تجربة المستخدم على الجهاز
  المُبطَل (توجيه تلقائي لشاشة انضمام جديدة) غير مكتملة.
- **لا تحويل كل الأقسام لسجلات مستقلة** (راجع §٦) — المقاضي فقط في هذه
  الدورة.
- تفاصيل P2 (Vite/TypeScript، فصل الملفات، PWA، إتاحة الوصول) لم تُلمَس
  إطلاقاً كما طُلب — الأولوية المطلقة كانت الأمان.
