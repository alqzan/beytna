# خطة النقل الإنتاجية — خطوة بخطوة

**لا شيء في هذه الخطة يُنفَّذ تلقائياً من هذا الفرع.** كل خطوة تحتاج Firebase
Console/CLI بصلاحية لا يملكها هذا الفرع تُنفَّذها أنت يدوياً بالضبط كما هو
مكتوب أدناه. لا تخطوة خطوة قبل التي قبلها — الترتيب مقصود لتفادي قفل
البيانات قبل نقلها، أو تركها عامة بعد النقل.

## نظرة عامة على التسلسل

```
[الآن]  قواعد قديمة مفتوحة + families/beytna
   │
   ├─ 1) نسخ احتياطي من families/beytna (قراءة فقط)
   │
   ├─ 2) مراجعة الفرع محلياً (اختبارات + بناء) — بلا لمس الإنتاج
   │
   ├─ 3) إنشاء بيت جديد + دعوة الجهاز الثاني (لا يزال families/beytna يعمل بالتوازي)
   │
   ├─ 4) استيراد النسخة الاحتياطية داخل البيت الجديد + تحقق يدوي على الجهازين
   │
   ├─ ⏸️  نقطة توقف — موافقتك صريحة مطلوبة هنا قبل المتابعة
   │
   ├─ 5) نشر firestore.rules الجديدة (يغلق families/beytna ويغلق الوصول العام)
   │
   └─ 6) نشر index.html المحدَّث (Hosting/الاستضافة الحالية) + مراقبة
```

---

## الخطوة ١ — نسخ احتياطي من المستند القديم (قبل أي شيء آخر)

**لماذا الآن**: قواعد الإنتاج الحالية لا تزال مفتوحة (هذا ما نغلقه)، لذا
هذه آخر فرصة للقراءة بدون Auth. هذا **قراءة فقط**، لا كتابة.

1. من داخل هذا الفرع محلياً: `npx serve .` (أو أي خادم ملفات ثابتة بسيط).
2. افتح `http://localhost:PORT/migration/backup-legacy-doc.html`.
3. اضغط "قراءة ونسخ families/beytna احتياطياً".
4. سيُنزَّل ملفان:
   - `beytna-legacy-RAW-backup-<تاريخ>.json` — نسخة خام كاملة (أرشفة).
   - `beytna-legacy-IMPORT-READY-<تاريخ>.json` — جاهزة للاستيراد من داخل
     التطبيق الجديد مباشرة.
5. احتفظ بالملفين في مكان آمن (ليسا سريّين تقنياً لكنهما بيانات عائلية —
   لا ترفعهما لأي مكان عام، لا تضعهما في PR أو logs أو screenshots).

**تحقق**: الأرقام المعروضة في نهاية الأداة (عدد أغراض المقاضي/الملاحظات/
الوجهات/أغراض الشنطة) تطابق ما تتوقعه فعلياً من التطبيق الحالي.

## الخطوة ٢ — مراجعة الفرع محلياً (بلا لمس الإنتاج)

```bash
npm install
npm run lint
npm run test:unit
npm run test:rules     # يشغّل Firebase Emulator محلياً — لا يلمس beytna-1 الحقيقي
npm run build
```

كل هذه الأوامر تعمل محلياً/عبر Emulator فقط. `npm run test:smoke` يحتاج
اتصال إنترنت عادي (يحمّل Firebase من gstatic CDN كما يفعل التطبيق
الحقيقي) — إن كانت بيئتك تسمح بذلك شغّله أيضاً.

---

## الخطوة ٣ — إنشاء البيت الجديد ودعوة الجهاز الثاني

هذا **لا يمس** `families/beytna` ولا القواعد الحالية إطلاقاً — البيت
الجديد يُنشأ بمعرّف عشوائي منفصل تماماً، ويعمل بالتوازي مع التطبيق القديم.

1. افتح `index.html` (نفس الاستضافة الحالية، أو محلياً عبر خادم ثابت)
   على **الجهاز الأول**.
2. اختر "بيت جديد" → أدخل اسم الجهاز (اختياري) → "إنشاء بيتنا".
3. ستظهر شاشة فيها رمز دعوة (نص واحد بصيغة `familyId.token`) — انسخه أو
   شاركه.
4. على **الجهاز الثاني**: افتح نفس `index.html` → "الانضمام لبيت موجود"
   → الصق الرمز → "انضمام".
5. تحقق أن كلا الجهازين يريان نفس البيت الفارغ الجديد.

---

## الخطوة ٤ — استيراد النسخة الاحتياطية + تحقق يدوي

1. من أي من الجهازين: الإعدادات ⚙️ ← "نسخة احتياطية" 💾 ← "اختيار ملف
   نسخة احتياطية" ← اختر `beytna-legacy-IMPORT-READY-<تاريخ>.json`.
2. ستظهر معاينة بالأعداد — تحقق أنها تطابق ما لاحظته في الخطوة ١.
3. اختر "دمج مع الحالي" (البيت الجديد فارغ أصلاً، فالدمج والاستبدال
   متكافئان هنا، لكن الدمج أكثر أماناً كعادة) ← "تأكيد الاستيراد".
4. **تحقق على الجهازين معاً**:
   - المقاضي: نفس الأغراض على الجهازين، والتعديل من جهاز يظهر فوراً
     على الآخر (أضف/علّم غرض من جهاز، راقبه يظهر خلال ثوانٍ على الآخر).
   - الملاحظات/السفر/الشنطة: نفس المحتوى على الجهازين.
   - جرّب تعديل عنصرين مختلفين من الجهازين في نفس الوقت تقريباً — تأكد
     أن كليهما يبقى (لا مسح لتعديل الطرف الآخر).

إن وجدت أي خلل هنا: **لا تكمل للخطوة التالية**. البيت القديم `families/beytna`
لا يزال يعمل بلا أي تغيير — ارجع له، أصلح المشكلة، وأعد المحاولة من
الخطوة ٣ ببيت جديد آخر (لا كلفة لإعادة المحاولة، لا شيء أُغلق بعد).

## ⏸️ نقطة توقف — موافقة صريحة مطلوبة

لا تنتقل للخطوة ٥ إلا بعد:
- [ ] تأكيد الخطوة ٤ نجحت على الجهازين فعلياً (لا افتراض).
- [ ] نسخة `beytna-legacy-RAW-backup-*.json` محفوظة في مكان آمن.
- [ ] **موافقتك الصريحة** (أنت، صاحب الحساب) على المتابعة للخطوة ٥ —
      لأن الخطوة ٥ تُقفل `families/beytna` بلا رجعة سهلة عبر التطبيق
      (البيانات تبقى موجودة في Firestore، لكن لا طريقة عادية للوصول لها
      بعد نشر القواعد الجديدة إلا عبر Console/عكس القواعد يدوياً).

## الخطوة ٥ — نشر قواعد Firestore الجديدة (تغلق الوصول العام)

**هذه الخطوة تحتاج Firebase Console أو CLI بصلاحية على مشروع `beytna-1`
لا يملكها هذا الفرع.** نفّذها يدوياً بإحدى الطريقتين:

### عبر CLI (مفضّل — نفس محتوى `firestore.rules` بالضبط من هذا الفرع):
```bash
npx firebase login
npx firebase deploy --only firestore:rules --project beytna-1
```

### أو عبر Console يدوياً:
1. افتح https://console.firebase.google.com/project/beytna-1/firestore/rules
2. الصق **محتوى ملف `firestore.rules` من هذا الفرع بالضبط** (لا تكتب
   قواعد من الذاكرة أو تخمين — انسخ الملف حرفياً).
3. اضغط "نشر" (Publish).

**تحقق فوري بعد النشر** (من متصفح بدون تسجيل دخول، أو من `curl`):
- محاولة قراءة أي مستند `families/*` بدون Auth يجب أن تُرفض
  (`PERMISSION_DENIED`).
- التطبيق الجديد (بيت الخطوة ٣) يستمر يعمل طبيعياً على الجهازين (لأن
  القواعد الجديدة تسمح بعضويته الصحيحة).
- فتح `families/beytna` (حتى بمعرفة الرابط المباشر) يُرفض للجميع.

## الخطوة ٦ — نشر `index.html` المحدَّث

انشر ملفات هذا الفرع (`index.html`, `lib/`, الأيقونات) على نفس استضافة
الإنتاج الحالية (مهما كانت — GitHub Pages/Firebase Hosting/غيرها) بنفس
الطريقة المعتادة. **لم يتغيّر شكل الاستضافة نفسه في هذه الدورة.**

بعد النشر: تأكد أن أي مستخدم يفتح الرابط القديم على جهاز لم يُهيَّأ بعد
يرى شاشة "بيت جديد / الانضمام لبيت" (لا شاشة بيانات فارغة موهمة بأن كل
شيء اختفى) — وأن الجهازين اللذين أنشآ/انضما في الخطوة ٣ يستمران يعملان
بلا أي إجراء إضافي منهما (الجلسة محفوظة محلياً).

## Rollback — إن فشل شيء بعد الخطوة ٥

- **البيانات القديمة لم تُحذف أبداً** — `families/beytna` لا يزال موجوداً
  في Firestore بكامل محتواه، فقط مقفول بالقواعد. لا فقدان بيانات ممكن من
  هذه الخطة وحدها.
- إن فشل التطبيق الجديد على أحد الجهازين بعد النشر:
  1. لا تحذف/تنقل شيئاً. البيانات في `families/beytna` وفي البيت الجديد
     كلاهما آمن.
  2. لأصحاب صلاحية Console: يمكن مؤقتاً إعادة قواعد أكثر انفتاحاً
     (مثلاً السماح بالقراءة العامة مرة أخرى) **فقط كخطوة طوارئ مؤقتة**
     لاستعادة الوصول الفوري، مع فتح مشكلة لإصلاح السبب الجذري فوراً —
     هذا يُعيد نفس الثغرة الأصلية مؤقتاً، فلا يُستخدم إلا كحل طوارئ قصير
     جداً بينما يُصلَح الخلل.
  3. الأفضل: أصلح الخلل في `firestore.rules` أو `index.html`، اختبر عبر
     `npm run test:rules`/`npm run test:smoke` محلياً، ثم أعد نشر
     الإصلاح (الخطوة ٥/٦ مرة أخرى) — لا حاجة لأي "تراجع" فعلي لأن لا شيء
     دُمِّر.
- النسخ الاحتياطية (`beytna-legacy-RAW-backup-*.json` و
  `beytna-legacy-IMPORT-READY-*.json`) تبقى صالحة للاستيراد من جديد في
  بيت آخر في أي وقت، بغض النظر عن حالة `families/beytna` أو القواعد.

## متى نحذف `families/beytna` فعلياً؟

**لا نحذفه في هذه الدورة على الإطلاق.** يبقى مقفولاً بالقواعد إلى أجل غير
مسمى كنسخة احتياطية إضافية داخل Firestore نفسه. حذفه الفعلي (لو أردته
لاحقاً لتوفير مساحة) قرار منفصل يحتاج تأكيدك الصريح في دورة قادمة، بعد
تأكّد تام أن البيت الجديد مستقر لفترة كافية على الجهازين.
